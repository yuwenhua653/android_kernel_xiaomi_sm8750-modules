# R17: native Android module staging

R17 turns the R16 audio/network plans into real Android module directory
contents. It does not add another driver or complete the device ROM. Kernel
code, DT candidates and the 91 external module build are unchanged from R16;
the matching kernel is the R14 `6.6.144-4k-gf112270e61a8` build.

## Observed integration gaps

The exact OS4.0.6.0.XPKCNXM vendor partition was extracted and checked against
the payload partition hash:
`2601a8eb5879617858263ae7365dbd1bbbd8db79926ff2565ee950bbe1c676bc`.
This is payload integrity, not verification of the OTA's signing chain.

Its `system_dlkm_modprobe.sh` scans version subdirectories beneath
`/system_dlkm/lib/modules`. It would skip the flat directory generated by the
source configuration used here. The vendor script starts later modules in
parallel and sets `vendor.all.modules.ready=1` after waiting without checking
every child status. An ordered candidate list alone therefore does not enforce
R16's board dependency order or reliably report insertion failures.

The proprietary scripts are not imported. `annibale_native_loader.sh.in` is
an independent source-native implementation. HyperOS retains its original
coherent stock modules, DT, firmware and loading configuration.

The exact vendor `lib64/libagm.so` contains the smartpa sysfs path, TFA/SIA
family strings and the persistent smartpa property name. This confirms that
the R16 read ABI is referenced by the supplied userspace binary; strings alone
do not establish executed control flow, property precedence or SELinux access.
R17 does not force an amplifier property or infer which amplifier is fitted.

## Reproduce staging

```sh
python3 -B sm8750-modules/tools/stage_annibale_android.py \
  --kernel-out out/annibale-btf \
  --module-stage out/annibale-modules-r16/MODULE_STAGE \
  --policy sm8750-modules/Documentation/xiaomi/annibale-audio-tfa-partitions.json \
  --depmod tools/kernel-build-tools/linux-x86/bin/depmod \
  --strip tools/clang-selected/clang-r510928/bin/llvm-strip \
  --odm-root /path/to/exact/OS4/odm \
  --output out/annibale-tfa-android
```

Use the completed R16 build directory in place of MODULE_STAGE. For SIA use
the SIA policy and a different new output directory. Neither the output nor
the build/source directories are overwritten. The optional ODM input performs
the R16 asset hash/header/XML checks; **it does not copy proprietary files**.
An omitted ODM check is not evidence that firmware is available.

The implementation follows LineageOS 24 build rules at
[`android_build` 90d0063](https://github.com/LineageOS/android_build/blob/90d006387398ae6899145e6531a304500cfa0f70/core/Makefile):

| Partition | Module files | Runtime dependency path | Count TFA / SIA |
| --- | --- | --- | --- |
| vendor_boot | `vendor_boot/lib/modules` staging subtree | `/lib/modules` | 32 / 32 |
| system_dlkm | `system_dlkm/lib/modules` | `/system/lib/modules` | 1 / 1 |
| vendor_dlkm | `vendor_dlkm/lib/modules` | `/vendor/lib/modules` | 89 / 90 |

The vendor_boot subtree is a staging convention, not a boot image or a
literal directory to add to the ramdisk. Android places its contents at
`/lib/modules`. `/system/lib/modules` and `/vendor/lib/modules` require the
standard symlinks to their respective DLKM partitions and first-stage mounts.

Vendor and vendor-ramdisk modules undergo `llvm-strip --strip-debug`; system
modules retain upstream's unstripped behavior. Each output is checked against
its original ELF for modinfo, versioned imports, exported CRCs and BTF sections.
Signed modules are rejected before stripping rather than silently invalidating
their signatures. This is not a signing/trust validation or proof of runtime CFI.

Real host depmod generates `modules.dep`, `modules.alias`, `modules.softdep`
and ordered `modules.load` files. Text dependency paths are rewritten as in the
Android build. Every record/path and available hard dependency is checked.
Vendor depmod includes system modules as additional providers, not ramdisk
modules, matching upstream. The latter must already be loaded; generated
scripts check every selected vendor_boot module in `/sys/module` first.
No synthetic exports, stock modules, fabricated builtins, binary depmod indexes
or permissive unresolved-symbol workarounds are inserted.

## Native loader integration

The generated scripts load the flat system list and then the vendor list
serially. They reject a wrong kernel release, missing preloaded modules,
missing indexes/files, malformed list entries and failed modprobe calls. A
successful call must also leave the canonical module name in `/sys/module`.
The vendor script clears `vendor.all.modules.ready` before starting and sets
it only after all configured insertions succeed. It repeats the system
prerequisite itself because init can continue after a failed system service.
Already loaded modules are accepted by Android modprobe.

The property denotes completion of **this configured module list**, not
successful device probes or complete hardware readiness. It must not be
enabled as a full-device signal until the module plan covers the entire ROM.
No extra loader services or new SELinux properties are introduced.

Review the generated `BoardConfig.modules.mk.example` and
`Product.modules-loader.mk.example` in the actual device tree. They use
standard Android variables and reject existing variable/copy owners. Also
remove/review conflicting Soong prebuilt owners, stock archives, legacy
audio blocklists, existing prebuilt kernel/DT settings and recovery lists;
Make guards cannot detect every possible owner. Keep the existing
`gki.modprobe` and `vendor.modprobe` services and replace their script copy
owners exactly once. The inspected OS4 policy labels both script paths as
`vendor_modinstall-sh_exec` and the ready property as `vendor_modprobe_prop`.
Native policy, `/sys/module` access and vendor tool availability still need
validation in the actual built image under enforcing SELinux.

Do not append the qualification subset to stock module lists or install both
amplifier families. Select the DT and source policy together only after actual
hardware identification. These examples are deliberately not included by a
live BoardConfig and do not modify the reference prebuilt ROM tree.

## Firmware and remaining validation

LineageOS 24's
[`system/core` 65d661b ueventd configuration](https://github.com/LineageOS/android_system_core/blob/65d661b1a536701e8b118be4e9728d7b5ca727c9/rootdir/ueventd.rc)
already searches `/odm/firmware/`. The pinned TFA container or SIA firmware
therefore has a standard userspace fallback location; it does not need an
invented extra search directory. This still depends on mounted ODM,
ueventd/SELinux, firmware fallback and actual driver request behavior.
Preserve the matching selected ACDB, amplifier init and mixer/resource XML
ownership. Keep per-device persist calibration on its original device. DSP
firmware/topology and the complete HAL dependency closure remain unqualified.

Host tests execute the generated shell with isolated stub tools; they test
ordering and failure propagation, not Android runtime execution. The actual
TFA and SIA stages both pass depmod/path and strip-invariance checks. There is
no newly built boot/vendor_boot/DLKM filesystem image, no flash package, and
no new device boot/audio result. The retained-stock audit's eight unresolved
normal/recovery variants remain unresolved; R17 does not turn HyperOS into a
combined compatibility pass.

The next integration gate is a complete selected module plan, real device-tree
ownership conversion, final partition contents/signatures and an enforcing
init/mount/probe check. Until then these are reproducible installation
qualification artifacts, not a recommendation to flash.
